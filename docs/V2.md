# URL Shortener — V2

V2 moves the URL Shortener from a single-container local application to a **distributed AWS architecture**.

The main goals were to introduce **multiple application instances, a shared PostgreSQL database, load balancing, health checks, and AWS networking**.

## Architecture

```text
                         Internet
                            |
                            v
             Application Load Balancer
                            |
                    +-------+-------+
                    |               |
                    v               v
                 EC2 #1          EC2 #2
                    |               |
                    +-------+-------+
                            |
                            v
                    RDS PostgreSQL
```

The application instances run independently, while both connect to the same PostgreSQL database.

## V1 → V2

### V1

```text
FastAPI
   |
 SQLite
```

The application and database were tied to a single container.

### V2

```text
                         ALB
                       /     \
                      v       v
                   EC2 #1  EC2 #2
                      \       /
                       \     /
                        v   v
                    PostgreSQL
                        |
                       RDS
```

V2 separates the application and database layers and introduces an entry point capable of distributing traffic across multiple application instances.

## What Changed?

| V1                          | V2                                 |
| --------------------------- | ---------------------------------- |
| SQLite                      | PostgreSQL on Amazon RDS           |
| Single application instance | Two EC2 instances                  |
| Direct application access   | Application Load Balancer          |
| Local database              | Shared external database           |
| Single container            | Multiple application instances     |
| Local environment           | AWS VPC                            |
| No health-based routing     | ALB health checks                  |
| No network segmentation     | Public/private subnet architecture |

## AWS Infrastructure

V2 uses the following AWS components:

* Amazon VPC
* Public and private subnets
* Internet Gateway
* Route tables
* Security groups
* EC2
* Application Load Balancer
* Amazon RDS for PostgreSQL

## Network Architecture

The application is deployed inside an Amazon VPC.

```text
                         Internet
                            |
                            v
                    Internet Gateway
                            |
                            v
                    Public Subnets
                     +------------+
                     |    ALB     |
                     +------------+
                       /        \
                      /          \
                     v            v
              Application     Application
                EC2 #1          EC2 #2
                     \            /
                      \          /
                       v        v
                    Private Subnets
                       +--------+
                       |  RDS   |
                       |Postgres|
                       +--------+
```

The Application Load Balancer and application instances are placed in the public-facing part of the architecture, while the database is isolated in private subnets.

The database is not directly exposed to the internet.

## Security Groups

Traffic is controlled using separate security groups for the different layers.

### ALB Security Group

Allows:

```text
Internet → ALB
```

on the required application port.

### EC2 Security Group

Allows application traffic from:

```text
ALB → EC2
```

rather than allowing unrestricted access from the internet.

### RDS Security Group

Allows PostgreSQL traffic only from:

```text
EC2 → RDS
```

This creates a basic layered network model:

```text
Internet
   |
   v
 ALB
   |
   v
 EC2
   |
   v
 RDS
```

## Load Balancing

The Application Load Balancer distributes incoming requests across the available EC2 instances.

For example:

```text
                ALB
              /     \
             v       v
          EC2 #1   EC2 #2
```

If both instances are healthy, traffic can be distributed between them.

If an instance fails its health checks, the ALB can stop routing new traffic to that unhealthy target.

This provides **application-level availability and traffic distribution** without requiring the client to know which EC2 instance is serving the request.

## Health Checks

V2 introduces two application endpoints with different purposes.

### `/live`

Used by the Application Load Balancer to determine whether the application instance is alive and able to serve requests.

```text
GET /live
```

A successful response indicates that the application process is running.

### `/ready`

Used to verify that the application can communicate with the PostgreSQL database.

```text
GET /ready
```

This separates application liveness from database readiness.

Conceptually:

```text
/live
  |
  +-- Is the application running?

/ready
  |
  +-- Can the application reach PostgreSQL?
```

## Database

V1 used SQLite inside the application container.

V2 replaces SQLite with **PostgreSQL hosted on Amazon RDS**.

This provides a shared database that both application instances can access:

```text
        EC2 #1
           \
            \
             → RDS PostgreSQL
            /
           /
        EC2 #2
```

The application instances therefore do not maintain separate databases.

## Example Request

A client sends a request to the ALB:

```text
POST http://<ALB-DNS>/shorten
```

The request flow is:

```text
Client
  |
  v
ALB
  |
  +------> EC2 #1
  |
  +------> EC2 #2
             |
             v
        RDS PostgreSQL
```

The generated short URL is then returned to the client.

Redirect requests follow the same path through the ALB and application layer.

## Failure Scenario

If one EC2 instance becomes unavailable:

```text
                ALB
              /     \
             X       ✓
          EC2 #1   EC2 #2
                      |
                      v
                  RDS
```

The ALB health check detects that EC2 #1 is unhealthy and stops sending new traffic to that instance.

EC2 #2 can continue serving requests.

This improves availability compared with the single-instance V1 architecture.

## Limitations

V2 improves the architecture significantly, but infrastructure and deployments are still largely manual.

V2 does not yet include:

* Infrastructure as Code
* Automated CI/CD
* Container image registry
* Centralized monitoring
* Automated alerting
* Auto Scaling
* HTTPS/custom domain

These limitations motivate **V3**, where infrastructure and deployment are automated.

## V2 → V3

V2:


