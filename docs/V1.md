# URL Shortener — V1

V1 is the initial version of the URL Shortener project.

The goal of V1 was to build a working backend application with **FastAPI, SQLite, configuration management, logging, testing, and Docker**.

## Architecture

```text
Client
  |
  v
FastAPI
  |
  v
SQLite
```

The application runs as a single container and uses SQLite for persistent application data.

## Features

* Create short URLs with `POST /shorten`
* Redirect to the original URL with `GET /{code}`
* Database health check with `GET /health`
* SQLite database persistence
* Environment-based configuration
* Application logging
* Automated tests with pytest
* Dockerized application

## Technology Stack

* Python
* FastAPI
* SQLite
* pytest
* Docker
* uv

## Running Locally

Install the project dependencies:

```bash
uv sync
```

Start the FastAPI application:

```bash
uv run uvicorn app.main:app --reload
```

The application will be available at:

```text
http://localhost:8000
```

Interactive API documentation:

```text
http://localhost:8000/docs
```

Health check:

```text
http://localhost:8000/health
```

## Running Tests

Run the test suite with:

```bash
uv run pytest
```

## Running with Docker

Build the Docker image:

```bash
docker build -t urlshortener:v1 .
```

Run the container:

```bash
docker run --rm -p 8000:8000 --env-file .env urlshortener:v1
```

The API will then be available at:

```text
http://localhost:8000
```

## API Example

Create a short URL:

```bash
curl -X POST http://localhost:8000/shorten \
  -H "Content-Type: application/json" \
  -d '{"url":"https://www.google.com"}'
```

The application returns a short URL containing the generated code.

The short URL can then be accessed with:

```text
GET /{code}
```

which redirects the client to the original URL.

## Configuration

Application configuration is provided through environment variables.

For local development, create a `.env` file containing the required configuration.

> Do not commit `.env` files containing secrets to the repository.

## Limitations

V1 is intentionally designed as a **single-instance application**.

### SQLite

The SQLite database is stored in the container filesystem.

This means that:

* A second application container would have its own database.
* Multiple instances cannot safely share the same SQLite database.
* Recreating the container can result in loss of database data unless persistent storage is configured.

### Single Application Instance

V1 does not include:

* Application Load Balancer
* Multiple application instances
* External database
* High availability
* Infrastructure as Code
* CI/CD
* Centralized monitoring
* Automated deployment

These limitations motivated the architecture changes introduced in **V2**.

## V1 → V2

The main limitation of V1 is that the application and database are tightly coupled to a single container.

V2 separates the application layer from the database and introduces multiple application instances:

```text
V1

FastAPI
   |
 SQLite
```

becomes:

```text
V2

              ALB
             /   \
            v     v
         EC2 #1 EC2 #2
            \     /
             \   /
              RDS
```

This allows the application to run across multiple instances while sharing a central PostgreSQL database.
