# URL Shortener — V3

V3 extends the V2 AWS architecture with **Infrastructure as Code, container image management, automated CI/CD, monitoring, and alerting**.

The goal of V3 was to automate the infrastructure and application deployment process instead of managing these steps manually.

## Infrastructure as Code

V3 uses **Terraform** to define the AWS infrastructure.

Terraform manages resources including:

* VPC
* Subnets
* Route tables
* Internet Gateway
* Security groups
* EC2 instances
* RDS PostgreSQL
* Application Load Balancer
* Target groups
* ALB listeners
* ECR repository
* CloudWatch resources
* SNS
* IAM roles and policies

The infrastructure can therefore be recreated from the Terraform configuration rather than being configured manually through the AWS console.

## Container Registry

V3 introduces **Amazon Elastic Container Registry (ECR)**.

Instead of building the Docker image manually on each EC2 instance:

```text id="p5f9g2"
Source Code
    |
    v
Docker Build
    |
    v
ECR
```

The EC2 instances can retrieve the application image from the central ECR repository.

This separates **image creation** from **application execution**.

## CI/CD Pipeline

GitHub Actions automates the application deployment process.

The high-level workflow is:

```text id="h7jv8k"
                    git push
                       |
                       v
                GitHub Actions
                       |
             +---------+---------+
             |                   |
             v                   v
          Run Tests          Build Image
                                 |
                                 v
                                ECR
                                 |
                                 v
                            Deploy EC2 #1
                                 |
                                 v
                           Health Check
                                 |
                                 v
                            Deploy EC2 #2
                                 |
                                 v
                           Health Check
```

### Pipeline Stages

#### 1. Test

The application test suite is executed before deployment.

```bash
uv run pytest
```

If the tests fail, the deployment does not proceed.

#### 2. Build

GitHub Actions builds the Docker image from the project Dockerfile.

#### 3. Push

The image is tagged and pushed to Amazon ECR.

#### 4. Deploy

The EC2 instances retrieve the new image and restart the application using the updated container.

#### 5. Health Check

After each deployment, the workflow checks the application's health endpoint.

A deployment is considered successful only after the application responds successfully.

## Deployment Flow

The application is deployed sequentially:

```text id="4g2xql"

              |
              v
           EC2 #1
              |
         Health Check
              |
              v
           EC2 #2
              |

```

This allows the deployment process to verify each instance individually.

## IAM

V3 uses **IAM roles and policies** to provide AWS permissions to the required components.

For example, EC2 instances can be given permissions to retrieve container images from ECR without requiring long-lived AWS credentials to be stored on the server.

GitHub Actions also uses AWS credentials with permissions required for the deployment workflow.

The goal is to provide the required permissions while avoiding unnecessary access.

## Monitoring

V3 introduces **Amazon CloudWatch** for infrastructure monitoring.

CloudWatch monitors resources including:

* EC2
* Application Load Balancer
* RDS

Metrics can be used to identify abnormal resource usage or infrastructure problems.

## Alerting

CloudWatch alarms are configured for selected infrastructure metrics.

The alerting flow is:

```text id="l7mt9w"
AWS Resource
     |
     v
CloudWatch Metric
     |
     v
CloudWatch Alarm
     |
     v
SNS Topic
     |
     v
Email Notification
```

This allows infrastructure problems to generate notifications without requiring manual inspection of the AWS console.

## Application Health

The `/live` endpoint is used as part of deployment and infrastructure health verification.

```text id="5cn2qf"
GET /live
```

The deployment workflow checks this endpoint after updating each EC2 instance.

The Application Load Balancer also uses health checks to determine whether an EC2 instance should receive traffic.

This provides health verification at both the deployment and load-balancing layers.

## Current Limitations

V3 is a portfolio and learning project rather than a production platform.

The current architecture does not yet include:

* Auto Scaling
* HTTPS/custom domain
* Blue/green or canary deployments
* Managed secret storage such as AWS Secrets Manager
* Full application-level observability
* Distributed tracing
* Automated rollback

These would be potential next steps for a future version.
